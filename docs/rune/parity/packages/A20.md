## What dependents must know

- **A part that wants a folder from the user asks `crate::chooser::floating`.** "Send to…" (devices) is GTK's other user of the destination chooser, with a root limit and its own validator (`show_send_to_folder_dialog`); it has not landed on Rune, and when it does it adds a `Destined` kind there rather than a second chooser.
- **One browser window per process.** `host/floating.rs` keeps one browser (`BROWSER`) and one open chooser (`OPEN`) per thread, which holds while `strata-rune` opens one browser window and New Window does not open a second in process. A part that opens a second browser window in process keeps them per window.
- **`--qa --portal` runs on the session host too.** A portal run with `host = "session"` gets real chooser windows in the private sway, and the portal's chooser windows take foreign drops. A host that needs another window of the portal adds it to `qa::session::portal`'s registry.
- **A chooser's keys follow GTK's chooser key handling, in both modes.** The window's commands GTK's chooser has no stage for do nothing from a key there (`chooser::declines_key`): the clipboard, Duplicate, Undo and Redo, Copy path, Open With, open in a new tab, New Folder with Selection, the jump-to-folder prompt, Terminal, Compress, the custom actions, the tab commands, Settings and Search. Only the stages GTK's chooser reaches through `handle_chooser_key` may run them (`reached_from_chooser`). In default mode Space previews. In 10xer mode the chooser's refusals ("Not available in the file chooser", "Only one item can be chosen") come first among 10xer's keys, after an armed chord (`chooser::refuse_key`), and `chooser::tenxer` holds GTK's other guards: no pinning, local Go places only, no tab chord, and Escape cancelling. A part that adds a key command a chooser should not run adds it to `NOT_IN_CHOOSER`; one that adds a 10xer key a chooser should not run checks `app.chooser.is_active()` where GTK's 10xer path does.
- **The portal's session host aims at the first window of its process.** `Session::window` finds the window by pid (`sway.window(pid)`), and `resize` names it by pid, so with two chooser windows open at once the pointer's origin and a resize do not follow `adopt` to the second. No run opens two today; a run that does needs the session host to find the window by its sway id.
- **The QA backend's default host is `qa::windows::Windows`,** the browser plus a floating chooser. `Host::origin(node)` and `Activated::node` tell a host which window a node is in; a host with one window ignores them.

- **A chooser's `App` is `App::new_chooser`,** with `app.browser.is_chooser_mode()` and `app.chooser.active` set. A part that must behave differently in a chooser asks those; a chooser's menus carry no custom-action or provider sections, as GTK's `chooser_context` menus do not.
- **The sidebar's grip is 1 pt wide.** A scenario or test that aimed at the sidebar's edge with a few points of slack now lands on the sidebar's blank space, which A9 routes to a marquee.

- **The 10xer reference's chooser sections** ([A11](A11.md)'s note below): not ported. They are reached by no run.
- **On a real display the floating chooser is not transient for, or modal over, the browser window,** as GTK's is: Rune makes no window transient for one of the app's own ([Rune packet entry 23](../../upstream/rune/23-transient-for.md)), and P4 parents only to another process's window. It opens as a window of its own, one per browser window, which the host brings forward when asked for again and closes with the browser. On Wayland bringing it forward is only an attention request, which sway shows as urgent: Rune's `WindowHandle::focus` activates a Wayland window only with a forwarded XDG activation token, and at the pinned rev (`631e8a6`) Rune mints none from the app's own input, as GTK's `present` does. On X11 it takes the keyboard. No QA run covers the windowed host's floating chooser: the session host reads the browser's window only, and `window::qa::the_floating_chooser_comes_forward_and_closes_with_its_browser` covers its raise and close.
- **A Copy to or Move to that starts no transfer keeps its destination to navigate to,** as GTK's does ([#2588](https://github.com/lgse/strata/issues/2588), an `oracle` finding): `transfer_to_chosen` sets `Transfer::pending_navigate` before `begin_transfer`, which can return early (refused, all no-ops, or already preparing), and a later foreground transfer that reveals nothing then navigates there. Rune matches GTK until a fix lands on `main`.
