### The oracle: how GTK routes a press

One reader, then three controllers on the window, in this order.

1. **The reader** (`keys::on_press`, `src/ui/keys/mod.rs:102`). A field that is composing
   gets the key first (lines 113 to 124); an armed capture in the window takes every press
   but a lone modifier (126 to 128, `capture.rs:79`); then the press is read through the
   aliases, with `typing` true when a text field or a popover has focus or type-to-search is
   on (129 to 132, `alias.rs:18`).
2. **The tab strip**, a capture-phase controller (`TabWindow::handle_key`,
   `src/ui/window/composition/tabs.rs:754`): Escape cancels a tab drag, the number hints
   follow the held modifiers, then the tab keys (`is_tab_shortcut`, line 813) unless a modal
   layer is visible (`blocked`, lines 215 and 760). A tab's own dispatcher leaves those keys
   to it (`src/ui/window/keyboard.rs:141`).
3. **The dispatcher**, capture phase, so before the focused widget
   (`src/ui/window/keyboard.rs:132`). On entry it cancels a pending bookmark, which takes the
   press (line 136), and every press but a modifier's invalidates the open-with lookup and
   moves the bookmark revision on (lines 422 to 426). Then `handle_key` (line 421) is a
   chain: each stage answers "not mine" (the next stage is asked), "taken" or "the focused
   widget's" (the chain ends and GTK delivers the key). In its order, with the files under
   `src/ui/window/keyboard/`:

   | `input_owner` | `input_owner.rs:19` | Who owns input. A modal layer gets every key, and one that has lost the focus takes it back and swallows the key (lines 30 to 50).    **`after_yield` follows every answer but "taken"** (`keyboard.rs:147` to 150, 531),
   whether the chain was left or a stage gave the key to the focused widget. It runs the five
   window actions (search, jump to folder, terminal, refresh, arrow scope, line 56). An
   enabled action takes its key even when its guard then declines to run it (line 541), and
   the guard declines under a modal layer other than the action's own or an inline edit
   (`composition.rs:239` to 243). So those five keys act under a menu and in the location
   bar, and are swallowed under a dialog and in a rename. The terminal's is skipped in 10xer
   mode (line 550). With the F1 reference open, `after_yield` runs none of them (532 to
   534). Last come a text field's editing keys read through the layout fallback.
4. **What the focused widget does not take** bubbles to the Settings key
   (`composition/settings.rs:71`) and last to the native aliases (`alias.rs:45`).

**The window's chain is not the only reader.** About forty widgets install a key controller
of their own (the context menu's, dialogs, the location bar's completion, a pane's header,
the filter, open-with, the views' own). The rule for the Rune side: such a key is the
part's own handler in its own element, and it registers an action only if a menu row, a
button or a palette also runs the same command.

**Chords** are the 10xer stage's state: an armed chord reads the next press first, and most
owners cancel it. The default map has none. **`never_fires`** (`conflicts.rs:312`) is the
part of the conflict check a label uses: a binding no press can reach where its command
acts (no path in that map, a Shift a symbol consumes, a typed key behind the 10xer listing)
or a plain key a user added while type-to-search types it.

**A keyboard-opened menu** targets the browser's focused item when it is selected, else the
folder (`view_filter.rs:78`), anchored at the row's right edge or the pane's middle
(`columns.rs:191`, `browser_modes/context_menu.rs:53`). **What a menu acts on** is the
selection when the entry is in it, else the entry alone (`context_entries`,
`src/ui/browser/context_menu.rs:72`).

### What Rune gives: three places a press is heard

Rune has no capture phase. Its order for one key (`Runtime::route_key`,
`crates/rune/src/runtime/input/keys.rs` at the pin; the README's "Key routing" is the
summary):

1. Return and Escape go to a composition, and no further.
2. **Element handlers** (`El::on_key`): the focused element's, then each ancestor's,
   innermost first. Not called while a text field has focus, and not above a Rune modal.
3. Return presses the default button.
4. With nothing focused, the window's `on_key`.
5. A focused text field's own handler (`on_input_key`).
6. **Rune's focus navigation**, for a key with no Ctrl, Alt or Super: Escape dismisses a
   modal; Tab and Shift+Tab move focus; arrows, Home, End and type-select move inside a
   focus group; Space presses the focused control and Return a focused row.
7. A text field's editor: characters, the caret keys, and Ctrl with A, C, X, Z and Y.
8. **The window's `on_key`**, with something focused.
9. Selected text's copy keys, the Menu key's secondary press, page scrolling.

So a press reaches the registry at one of three entry points, and which one depends on who
has the keyboard:

| Who has the keyboard | Hears it first | The registry is asked at |
| --- | --- | --- |
| The shown view | Nothing | **Before the view** (a hook on its collection, ahead of its controllers): `TabStrip` to `Dismissal`. Then the view's controllers. Then **the root element's `on_key`**: `ItemNavigation`, `AfterYield`, `Unclaimed` |
| Another element outside a Rune modal that is no text field (a header button, a sidebar row) | That element's own `on_key`, if it has one | **The root element's `on_key`**, before Rune's default button and focus navigation: every stage |
| A text field | The field's own handler; then Rune's focus navigation (Tab) and the editor | **The window's `on_key`**: the stages its owner leaves (see `Holds`) |
| An element inside a Rune modal: a menu, a dialog | The modal's own handlers; then Rune's focus navigation (Escape, Tab, a menu's arrows, Space, Return) | **The window's `on_key`**: the stages its owner leaves |
| Nothing | Nothing | **The window's `on_key`**: every stage |

What this means for a stage, which the table of stages cannot say alone:

- **From the view, every stage is reachable, in GTK's order.** The view's controller hears
  a key only after the stages before `ItemNavigation` have declined it, as GTK's list does.
  Escape, Backspace, Delete, Space, Return, Ctrl+A and a letter under type-to-search
  therefore go to a registered action first, with no view remembering to ask.
- **From a text field, a stage hears only what the field passes on:** chords with Ctrl, Alt
  or Super other than the five editing ones, function keys, the page keys, Insert and the
  Menu key. Tab, Escape, Return and typed text never arrive. So `RenameTab` and
  `DefaultTabNavigation` are not reachable from a field through the registry: Tab in a
  rename is C5's own (it is today), and a component whose field must give GTK's chain a key
  it takes itself gets a hook in its own `contract` change. `strata-app` cannot attach one
  from outside: each component sets its field's `on_input_key`.
- **From inside a Rune modal, a stage hears chords and function keys only.** That is all
  the stages a modal leaves read in the shipped maps (text size, the tab keys, the five
  window actions).
- **A component with no key hook of its own** (a rune-kit button, a C21 menu row) gives the
  registry whatever Rune's focus navigation does not take; its Space and Return press it,
  as GTK leaves them to a focused button.
- **`FocusNavigation`** (arrows and Tab between the header, the sidebar and the panes) is
  reachable from the view and from any element under the root, because the root's handler
  runs before Rune's own focus navigation. No package has registered it yet; A3 is the
  first that needs it.

Measured at the pin on the offscreen host: the Menu key and Shift+F10 reach the window's
`on_key` after the Columns strip passes them on; and with a context menu open the window's
keys act today (Ctrl+H toggles hidden files under the menu), which GTK does not do.

A press is never walked twice. The window's `on_key` walks only when nothing is focused or
a part holds the keyboard (`Holds`, below); otherwise the root element's handler has
already asked every stage. So **a part whose element takes text or is a Rune modal answers
`Part::keyboard`**; until it does, the window's keys do not act while it has focus.

### The registry

A new module, `crates/strata-app/src/commands.rs`, owned by the contract.

```rust
/// One command, by every route: keys, a menu row, a header button, a palette.
pub(crate) struct Action<S: 'static> {
    /// The name a menu row or a button asks for it by: the row's id, the button's.
    pub(crate) id: &'static str,
    /// The catalog's command this is, when the catalog has it: what a palette and a label
    /// show its keys from, and what says the command has a path on this interface.
    pub(crate) command: Option<Command>,
    /// Where GTK's stages read its keys. Empty for a command no key runs.
    pub(crate) keys: &'static [Keys<S>],
    pub(crate) run: fn(&mut S, &Call<'_>, &mut Tx) -> Outcome,
}

/// One stage's reading of a command's keys.
pub(crate) struct Keys<S: 'static> {
    pub(crate) stage: Stage,
    pub(crate) reads: Reads,
    /// GTK's guard: `|_, at| !at.text()`.
    pub(crate) when: fn(&S, &Situation) -> bool,
}

/// What a stage matches a press against.
pub(crate) enum Reads {
    /// Catalog commands as the GTK stage has them: `RENAME.in_map(Map::Default)`,
    /// `REFRESH.ignoring(SHORTCUT_MODIFIERS)`.
    Commands(&'static [Matcher]),
    /// A digit range of the catalog: `TAB_NUMBERS`. The digit is the command's to read from
    /// the call's press.
    Digits(Digits),
    /// What neither says: a key that types, for type-to-search.
    Press(fn(&KeyPress) -> bool),
}

/// Where a command acts.
pub(crate) enum On {
    /// Where the keyboard is: a key, a header button, a palette.
    Focus,
    /// The row a menu was opened on.
    Row(At),
    /// A column's folder: a background menu.
    Column(usize),
}

/// One call: where, and the press when a key made it (its digit, what it typed).
pub(crate) struct Call<'a> { pub(crate) on: On, pub(crate) press: Option<&'a KeyPress> }

/// GTK's three answers of a stage.
pub(crate) enum Outcome { Ran, Declined, Left }
```

- **`Stage`** is the dispatcher's order as one enum, under GTK's names: `TabStrip`, `Entry`
  (what the dispatcher does on every press before its chain), the 21 rows of the table
  above, `AfterYield`, `Unclaimed` (the Settings key). Two commands on one press are decided
  by stage, then by the order the parts are registered, then by the order of a part's
  table: how GTK decides, and what `conflicts.rs` models.
- **An action is data tied to the catalog.** `command` names the catalog entry, and its
  keys are the catalog's own `Matcher`s and `Digits`. A matcher says which command, map and
  tolerated modifiers it reads (`Matcher::command`, `map` and `ignored`, added to the shared
  crate for this), so the registry can list every key a command answers and at which stage
  (`commands::bound(app)`): a palette's keys, a label's, an answer to `NeverFires` (a
  command with no keyed action has no path here) and a conflict check all read that list.
  `Reads::Press` is the escape hatch, for type-to-search, and is opaque to it.
- **Two names, one command.** A menu row and a button ask by `id` (the row's id, such as
  `hidden`); the catalog's id (`toggle_hidden_files`) is on the same action as `command`.
  A package lights a row by registering an action under the row's id, so `menus.rs` and
  `shell.rs` are not edited, and nothing else maps one name to the other.
- **Keys resolve through the shared catalog and both maps.** `Map::active()` is true on
  Rune from the registry's pull request on: the window registers an `Active`
  (`keys::set_active`) that reads the saved `tenxer_mode` and `type_to_search` at each
  press and each view, over `Keymap::defaults()`. A saved keymap joins there when B2's
  reader lands.
- **Every-press effects are actions at `Stage::Entry`** with `Reads::Press(|press|
  !press.is_modifier())`: one that answers `Declined` has seen the press and lets it go on
  (the open-with lookup, the bookmark revision), and one that answers `Ran` takes it (a
  pending bookmark). `Entry` runs under every owner. Its `when` sees `Situation::holds`, so
  the part that keeps a chord cancels it there when an owner has the keyboard. **It is not
  every press:** from a text field or a Rune modal `Entry` hears only what the field or the
  modal passes on, where GTK's dispatcher sees typed text too. So typing in a field cannot
  cancel a pending bookmark through the registry; the part that needs that hears the
  field's change itself.
- **One id, one action, among parts that are active together.** Two views may each register
  an id, since one is shown at a time. Any other repeat fails `Registry::check` when the
  window starts (`Fault::CommandTwice`), as a part registered twice does.
- **Builders are `const`**, as `menus::Row`'s are: `Action::new("rename", renamed)
  .command(RENAME).keys(&[Keys::at(Stage::InlineEditing, &[RENAME.in_map(Map::Default)])
  .when(|_, at| at.filter() || !at.text())])`, which is `rename.rs`'s.

The entry points, and nothing else calls a command:

```rust
/// Sets the collection hook: the stages before `ItemNavigation`, ahead of the view's controllers.
pub(crate) fn in_view(collection: Collection<App>) -> Collection<App>;
/// The root element's `on_key`.
pub(crate) fn from_element(app: &mut App, event: &KeyEvent, tx: &mut Tx) -> bool;
/// The window's `on_key`.
pub(crate) fn on_key(app: &mut App, event: &KeyEvent, tx: &mut Tx) -> bool;
/// A menu row, a header button, a palette.
pub(crate) fn run(app: &mut App, id: &str, on: On, tx: &mut Tx) -> Outcome;
/// Whether an active part has the command: what says a row or a button is not inert.
pub(crate) fn has(app: &App, id: &str) -> bool;
```

Each wraps the action in `shell::publish` and `shell::settle`. `Outcome::Left` ends the
walk and the entry point answers Rune "not taken", so the key goes to whatever is next in
Rune's order after that entry point: the view's controllers after `before_view`, the
default button and focus navigation after `from_element`, the selection's copy keys and
page scrolling after `on_key`.

A view passes its collection through `commands::in_view(collection)`, which sets the hook:
one line where the view configures its collection, and a line of "What a part writes" in
`slots.rs`. It needs one addition to strata-components, `Collection::before_keys`: a
handler `fn(&mut S, &KeyEvent, &mut Tx) -> bool` that the collection's key routing calls
ahead of its controllers (`route::on_key`, which already holds the state). It names nothing
of Strata's, takes the state by accessor and does no I/O, as Rune's own `on_input_key` on a
field. A controller cannot do it, having no way to the application state. The Columns
component needs no hook of its own: its strip sends a key to the active column's
collection (`strip_key`), and builds that collection through the closure the host gives
`ColumnsView::collection` (`hosted`, `columns/view.rs:509`), which is where the Columns
adapter already sets what it wants of each column. Three things make that hold:

- The hook is called inside `route::on_key`, the function a collection's own element
  handler and a host-keyed collection's `Collection::key` share. A `keys_by_host`
  collection gets no element handler of its own (`element/mod.rs:929`), so a hook placed
  there would never run for a strip.
- The strip scrolls the active column into view when its collection took a key
  (`strip_key`, `columns/view.rs:748`). A key the hook took is not the column's: the strip
  must tell the two apart and reveal only for the collection's own. GTK scrolls a column
  into view when one is added or kept and when the browser says the focus or the selection
  moved (the callers of `reveal_column`, `src/ui/browser/columns/strip_scroll.rs:104`),
  never for a window key as such.
- `ColumnsView::collection`'s documentation, which lists what a host may set there, names
  the hook.

The components' proof is a headless test, for a plain collection and for a Columns strip,
that a key the hook takes does not reach the controllers and one it declines does, and
that a key the hook takes does not scroll the strip. A test in `strata-app` presses a key in
every registered view and fails for one that left the line out.

### The part hooks

Two, in `slots::Part`, mirrored in `slots::registry::Entry` and `Entry::of`, read over
`Registry::active()`:

```rust
/// What this part's commands do, by any route.
const COMMANDS: &'static [commands::Action<App>] = &[];
/// What this part has of the keyboard now. Replaces `holds_keyboard`.
fn keyboard(_app: &App) -> Option<commands::Holds> { None }
```

`Holds` says which of GTK's owners the part is. The router holds GTK's rule for each, from
the lines cited above:

| `Holds` | GTK's owner | The chain runs through | `TabStrip` | `AfterYield` |
| --- | --- | --- | --- | --- |
| `Modal { field }` | A modal layer (`input_owner.rs:30`) | `ZoomShortcut` | Its commands do not run (`tabs.rs:760`) | The key is taken and nothing runs, but an action of the part that is the layer |
| `Menu` | A native menu (`input_owner.rs:21`) | `ZoomShortcut` | Runs | Runs |
| `Edit` | An inline edit (`commands.rs:85`) | `InlineEditing` | Runs | The key is taken and nothing runs |
| `Location` | The location bar (`commands.rs:177`) | `TextInput` | Runs | Runs |
| `Filter` | The filter's field | The end; `at.text()` and `at.filter()` | Runs | Runs |
| `Field` | Any other text field | The end; `at.text()` | Runs | Runs |

`Entry` and `Unclaimed` run under every owner. A modal layer says whether a text field of
its own has the keyboard: typing is then the field's, as under the three text owners
(`context_of` in `src/ui/keys/alias.rs`). The most restrictive answer among the active
parts wins. The rename editor answers `Edit` and the context menu `Menu`. A variant no part
answers yet carries an `expect(dead_code)` line, as the empty slots' `Place` variants do.

**The change of behaviour that comes with `Menu`:** today every window key acts under an
open context menu. After it, as on GTK, the chain's commands wait (hidden files, rename,
history) and text size, the tab keys and the five window actions still act: F5 refreshes
under a menu, through `AfterYield`.

Owners `Holds` does not cover, each one variant and one row of this table in the `contract`
change of the package that mounts it: the footer prompt, which answers for every key
(`input_owner.rs:72`); a focused file-operation card (`:52`); the open F1 reference, under
which `AfterYield` runs nothing; Settings' shortcut capture, which is above the tab strip.
A dialog on Rune is a Rune modal, which keeps the focus itself, so GTK's pulling the focus
back into a layer has nothing to port.

`Situation` is what a guard may ask:

| A guard asks | It reads |
| --- | --- |
| Whether text has focus, the filter, the location bar, an inline edit, a modal, a menu | `at.holds()`, with `at.text()` and `at.filter()` |
| Whether the listing has focus (`item_view_has_focus`) | `at.in_view()`: the focused key is the shown view's |
| Whether the sidebar, the header or the preview has (`sidebar.contains`, `top_bar.has_focus`, `preview.owns_focus`) | `at.within("sidebar")`: the focused element's key starts with the part's name, which is the rule for a part's keys |
| 10xer mode, the view mode, an open preview, an armed chord | The part's own state and the saved settings, from `app` |

Two things a guard must not assume. **A text field's editor keeps only Ctrl with A, C, X, Z
and Y:** Ctrl+V reaches the window's `on_key` from a field, so a registered Paste carries
`!at.text()`, as GTK's clipboard commands do ([A7](A7.md), [A12](A12.md)). **And `Entry` is
not every press** from a field or a modal (see "The registry").

`rewrite` gets `typing` from `at.text()`, a menu, or type-to-search.

The window's own commands (hidden files, refresh, history, parent, home, and the menu rows
Open and Select All) are a table in `commands/browser.rs`, read after the parts'. Rename's
moves to `rename.rs`.

### The header, and `menus::chosen`

- `shell::bar` builds its five buttons from a table of key, icon, label and command id
  (`toggle-sidebar`, `tab-new`, `search`, `appearance`, `settings`), and each press is
  `commands::run(app, id, On::Focus, tx)`.
- A chosen menu row runs the command whose id is the row's id (`open`, `rename`,
  `select-all`, `refresh`, `hidden`), on `On::Row` or `On::Column`. `Wired` and the `match`
  go.
- **No inert row is left unseen.** GTK draws every row enabled, so a row with no action is
  drawn as it is today and not greyed. `commands::has` is what tells: a test in `menus.rs`
  and one in `shell.rs` list the rows and the buttons that have no action, and the lists
  shrink to nothing as the areas land (the areas' done-when item 8).

### The Menu key

`commands::view_keys(collection, edge)` puts the menu's keys ahead of a collection's
keyboard controller, the one place a view's controller is wrapped: the Columns adapter calls
it for each column it adds, and `Single::new` on the collection it makes, so Icons and List
have it by construction. `Single::new` takes its values as `single::Made`, with `menu_at`,
where on the cursor's entry the menu opens: the centre in List, the right edge elsewhere.
The wrapper builds the press from the controller's `KeyInput` and matches the catalog's
`CONTEXT_MENU`, places the menu with C21's `keyboard_anchor`, and sends the
`Intent::ContextMenu` a press sends, which the view's handler gives the opener. It does not
use C21's `MenuKeys`, whose chords are Rune's and open with Super held; see "For the
owner". It sits in a controller and not in the registry because where the menu opens is
the collection's geometry, which only a controller is handed.

Which menu, as GTK's `open_focused_context_menu` reads it: the cursor's entry when it is
selected, with the selection it is in; the folder's otherwise, with a cursor outside the
selection or none. A menu key with anything else held opens nothing and is taken, so Rune
does not make a secondary press of it at the element's corner.

**A cursor scrolled out of view opens nothing, and nothing scrolls,** in every view. That is
what GTK's Columns and Icons views do, by a run on the GTK target; its List view opens the
menu of whichever entry is drawn where the cursor's row was last placed, and selects it
(finding [#2235](https://github.com/lgse/strata/issues/2235)), which this interface does not copy. A row partly in view gets its
own menu where it is drawn, as GTK does by a reading of its source; that case was not in
the run. C21's `keyboard_anchor` still says where the row
would land once revealed, and `MenuKeys` still reveals it; neither is used by this host.
The question is the owner's (`owner.md`).

That Icons opens nothing is by run and contradicts a reading of the source: the mode views
take the row's widget "mapped or not" (`item_widget`, `src/ui/browser_modes/pane.rs:75`),
which List's behaviour bears out and Icons' does not. Why was not traced.

### The press

`commands/press.rs` builds the `KeyPress` from Rune's `KeyEvent`, the physical key and the
base character (`tx.physical_key()` and `tx.key_base()`, or a controller's `KeyInput`), and
is the only code that does.

- **A named key** (`Enter`, an arrow, `Function(n)`, `ContextMenu`) is `from_parts` with
  `Typed::Key`.
- **A character** (`Text(c)` or `Command(c)`) is read with
  `KeyPress::from_signal(Key::from_char(c), keycode, held)`: the shared crate's own reading
  of the US table, the one `ui::keys` uses for a press without a GDK event, so no layout
  table is written a third time. The trap B2 names needs a legacy keysym, and
  `Key::from_char` never gives one. Ruled by the orchestrating session on 2026-11-12, with
  three conditions, which are the builder's rules:
  1. **The position.** Rune gives winit's `KeyCode`, not an X keycode. One function maps the
     48 keys of the main block to their X keycodes. It is a table of positions, not of what
     a layout types, and it is written once, there.
  2. **Caps Lock and AltGr, which Rune's `Mods` do not carry.** An uppercase character with
     no Shift is given with Lock held, so it reads as the letter and not as Shift with it.
     A character that is neither the key's base character nor typed with Shift is above
     level 1, on any key: it is given with no position, so it gets no Latin fallback and
     counts as a digit only if it types one. With Shift held, level 1 and level 3 cannot be
     told apart, and the position stands.
  3. **Rune's own substitution.** With Ctrl held on a layout that types no ASCII, Rune has
     already put the US key in the character's place. Where the base character says so, the
     builder gives the character the key really types, so `used_fallback()` is true as on
     GTK.
- **A keypad key with a known position** is its keypad key, as GDK reports it, by
  `from_parts`: a digit counts as a digit and types itself, an operator folds to the main
  key, and the decimal key stays a keypad key. Which one follows the character Rune
  delivers, as the layout decides it on GTK: `.` is `KP_Decimal` and `,` is
  `KP_Separator`.
- **Composed text of several characters** is `Typed::Nothing`.
- **A modifier's own press** is built with `held` as GDK reports it, without the key
  itself. Rune sends none unless the host asks (`modifier_keys`), and neither host does:
  the package that needs them (A4, whose tab-number hints follow a modifier going down and
  up) turns it on in both hosts, as a `contract` change, with the route for a release.

The seven cases, and an eighth:

| Case | The builder does | As GTK? |
| --- | --- | --- |
| 1. Another Latin layout configured | The US position | No, and not possible: Rune cannot see the other layouts. For the owner |
| 2. Above level 1 | No position, when the base character is known and Shift is not held | Yes in a window without Shift; not with Shift, and not in the QA target. One residue: a digit typed at such a level on a key outside the digit row counts as a digit here and not on GTK (`position_digit`, `keys.rs:654`) |
| 3. Keypad decimal and separator | The keypad key itself where the position is known | Yes in a window |
| 4. The QA target | No position and no base, so the US table reads the character: exact on a US layout, which every required run uses | Packet entry 97; a workaround outside Rune is H3's |
| 5. Keys Rune never delivers | Nothing arrives | Nothing to route |
| 6. A modifier's own press | `held` without the key | Yes |
| 7. Character to keysym | `Key::from_char`, B2's one keysym for a character | B2's |
| 8. A chord whose level types no ASCII on a key whose base is ASCII (found in review) | The US key Rune names: it has dropped the character typed, and an ASCII base does not say so | No: AZERTY Ctrl+Shift+`*` reads as Ctrl+`\`, Polish Ctrl+AltGr+A as Ctrl+A. For the owner; packet entry 100 |

### For the owner

Recorded in [`owner.md`](../owner.md#b3-commands-and-key-dispatch) with the pull request
that makes each true; neither is this package's to decide.

- **Super with the Menu key.** Rune reports Super, Hyper and Meta as one flag. GTK opens
  the menu with Hyper or Meta held and not with Super. C21 opens with the flag set, on
  purpose. In force until ruled: the flag is read as Super, the common key, so the menu
  does not open, as on GTK; Hyper and Meta then differ.
- **Where the Menu key is read.** `view_keys` opens the menu from a controller, so after
  every stage through `Dismissal`, where GTK's `context_menu_command` sits in the middle of
  the chain. No shipped key shows the difference.
- **Case 1.** For a user with a non-Latin layout and a non-US Latin one, a shortcut follows
  the US position where GTK follows the other layout: Undo and Redo trade places on QWERTZ.
  A deviation that needs the owner's word, with a packet entry for what Rune would have to
  report (99).
- **Case 8.** A chord at a Shift or AltGr level that types no ASCII, on a key whose base is
  ASCII, reads as the US key (packet entry 100).

## What dependents must know

- **A view opens a context menu with `menus::open(app, Request { depth, entry, anchor }, tx)`**
  from its handler for the collection's `Intent::ContextMenu { target, anchor }`, with
  `entry: target`. The opener ends an open rename, so the view does not; it asks the view
  only for `Rows::position`. A view whose rows are not the browser's (a filter, search
  results) has more to give it first, as a `contract` change to `Rows`.
- **The registry is `crates/strata-app/src/commands.rs`.** A key, a chosen menu row and a
  pressed header button each run the command registered under a name: `commands::run(app,
  id, on, tx)`. A menu row asks by its own id, a header button by `toggle-sidebar`,
  `tab-new`, `search`, `appearance` or `settings`. A row or a button whose name nothing
  registered is drawn and does nothing.
- **A part registers its commands in `Part::COMMANDS`,** a `const` table of
  `commands::Action`s, and says what it has of the keyboard in `Part::keyboard`. `rename.rs`
  is the example of both. A menu row runs the command registered under the row's id and a
  header button the one named for it, so neither `menus.rs` nor `shell.rs` is edited to
  light one. Two parts that are active together may not register one name
  (`Fault::CommandTwice`, when the window starts); two views may.
- **A part whose element takes text or is a Rune modal answers `Part::keyboard`.** The
  window's commands that GTK keeps from that owner then wait (`commands/owners.rs` has the
  rule for each), and a command's guard can ask `at.text()`. `holds_keyboard` is gone. Who
  answers what:
  - `Holds::Edit`: an inline edit while its field has the keyboard. `rename.rs` does
    ([A7](A7.md)).
  - `Holds::Menu`: an open context menu. `menus.rs` does ([A6](A6.md)).
  - `Holds::Location`: the location bar while it is edited ([A5](A5.md)).
  - `Holds::Filter`: the filter's field ([A10](A10.md)).
  - `Holds::Modal { field }`: the search palette and a dialog ([A10](A10.md), [A6](A6.md)).
    `field` is true while a text field of the layer has the keyboard: a letter typed there
    is text, where beside the field it is the arrow it stands for.
  - `Holds::Field`: any other text field.
- **Owners the GTK window has that `Holds` does not name yet.** Whoever mounts one adds it
  as a `contract` change to `commands/owners.rs`, with its row in the table test:
  - a popover that is not a menu (Appearance, a column's sort, Open With, the Back
    history): GTK counts focus in it as typing and switches off the 10xer keys and the
    default Tab there (`focus_navigation::in_popover`). `Holds::Menu` is the nearest, and
    cuts more;
  - a modal layer that is closing: GTK lets the window actions run again while it animates
    out (`modal_owner` in `src/ui/window/keyboard/input_owner.rs`). A part answers `None`
    from the moment it starts to close;
  - a background tab's root, which reads no key at all (`accepts_input` in
    `src/ui/window/keyboard.rs`). There is one root until [A4](A4.md).
- **With two parts answering `Part::keyboard` at once, the more restrictive is the owner,**
  and of two that answer the same `Holds` the one registered later, not the one drawn on
  top. Nothing stacks two modal layers today; the first package that does settles which is
  topmost, as a `contract` change.
- **A test that writes a `slots::Entry { … }` literal** has two fields in the place of
  `holds_keyboard`: `commands: &[]` and `keyboard: |_| None`. A part tests its own table
  with its `Entry` beside a made-up view in `test_support::hosted_over`, as
  `commands/tests/routing.rs` does.
- **A command reads its key ahead of the shown view's own keys** when it is registered at
  a stage ahead of `ItemNavigation`: Escape, Delete, Space, Return, Ctrl+A and a letter go
  to a registered command first, and the view's controller keeps each key no command takes.
  A command at `ItemNavigation`, `AfterYield` or `Unclaimed` hears what the view left.
  Rules that come with it:
  - **A view built on a collection calls `commands::in_view(collection)` once,** on each
    collection that takes its keys. `single::collection` does for Icons and List, and the
    Columns adapter in its `ColumnsView::collection` closure. A view that does not loses no
    command: the root element then asks every stage, but after the view's own keys, so no
    command can take a key that view's controller takes.
  - **How a press is walked once:** the hook notes the press it asked the early stages for
    (`commands/heard.rs`, `Stamp`), and the root element asks only the rest for that press
    and every stage for any other. No view has to be told apart from another element. The
    hook asks every press it is given, so a collection inside another that has the hook
    gets none of its own.
  - **A focused element Rune skips for element keys, whose part does not hold the
    keyboard, is asked nowhere:** a text field, or an element that can no longer take focus.
    Not reachable today. A part with such an element answers `Part::keyboard`.
  - **A command at an early stage that reads Escape takes it from a marquee** too: the hook
    is ahead of the collection's own cancel. Guard it (`Keys::when`) if it should not.
  - **A key the hook took does not reveal the Columns strip's active column.** GTK reveals a
    column when its cursor or the active column changes, not for a key.
  - **A part that answers `Part::keyboard` while the view still has the keyboard** is asked
    at the window, after the view's own keys: the elements' handlers stand back for an
    owner. A text field and a Rune modal take the keyboard from the view, so this does not
    arise for them.
  - **A test can press keys in the real views with a made-up part beside them:**
    `test_support::view::hosted_over_in` over `crate::parts_and(vec![…])`, as
    `commands/tests/views.rs` does.
- **A press is built in one place,** `commands/press.rs`, from Rune's event, the physical
  key and the base character. A part that hears a key in its own element and wants the
  catalog's answer calls `commands::read(app, event, &Situation::of(app, tx), tx)`, which
  takes the settings as they are now, builds the press and reads it through the aliases
  with the window's own rule for what owns typing; it then matches a catalog constant. It
  does not compare Rune's `Key` or spell a chord for `Keybind`.
- **`Map::active()` is true on Rune:** it follows the saved `tenxer_mode`, read at each
  press and each view, over `Keymap::defaults()`. A part that changes the mode or
  type-to-search with `shell::saved(app).change(…)` needs to tell nobody. Two limits:
  within one handler, a catalog read made after `Saved::change` still sees the old map,
  until the next press or view; and each view keeps its own copy of type-to-search, read
  once when the window starts (`Columns::with_settings`, and the single-pane views' own),
  which a change of the setting does not reach.
- **A command answers `Declined` only when it did nothing,** never after it changed
  something: the next command that reads the press would act on top of it, and Rune commits
  nothing for a key no handler took, so the change would not be drawn. `Ran` means the
  press is taken. `commands::run` and the walk already wrap each command in
  `shell::publish` and, when it ran, `shell::settle`, so a command does not call them for
  itself. What the browser had queued when a command declined is applied by the frame's
  `poll`, which runs the view for it.
- **The Menu key and Shift+F10 open the context menu in every view,** through the
  `Intent::ContextMenu` a secondary press sends. A view built on a collection of its own
  calls `commands::view_keys(&mut collection, edge)` once, after it has set the
  collection's controllers; `Single::new` and the Columns adapter do. A view whose rows are
  not the browser's needs nothing more for the key than it needs for a right-click.
- **`Situation::within(part)` takes the part's key prefix alone,** without a separator:
  `within("sidebar")` is true for `sidebar` and `sidebar-places`, and false for
  `sidebars`.
- **`commands/press.rs` is private to the registry.** `commands::read` is the one way to a
  press.
- **One name can mean different things by where it is asked** (`commands::On`): `refresh`
  reads every column again from a key and one column from the pane menu's row, and the two
  `properties` rows of the menus share an id. A command reads `call.on`.
- **Lighting a menu row or a header button means editing a pinned list:**
  `five_rows_have_a_command_and_the_rest_are_inert` in `menus/tests.rs` lists the rows that
  act, and `the_headers_buttons_wait_for_the_parts_that_own_their_commands` in
  `commands/tests.rs` the buttons that do not. Two packages' pull requests that each light
  one will conflict there; the resolution is to take both changes.
- **A test of this crate that runs in a process of its own goes through
  `test_support::in_own_process`,** as `hosted`, `hosted_in`, `hosted_over` and the QA
  mode's `staged` do. It fails a test whose path, as the string says it, is no test's: the
  child would run nothing and exit well (finding [#2193](https://github.com/lgse/strata/issues/2193)). A test in a nested module
  writes that module into its name.
- **Nothing catches a command with no keys that no row and no button names:** it can only
  be reached by `commands::run` from code, so check the name against the row's id or the
  button's by hand.

From [B2](B2.md), with the catalog's move ([#2195](https://github.com/lgse/strata/pull/2195)):

- **What is there:** `strata_desktop::keys` has `Key`, `Modifiers`, the catalog
  (`keys::bindings`), `registry()`, `Keymap`, `KeyPress` with `from_parts`, `rewrite` and
  the labels. `docs/rune/shared-state.md`, "The key catalog", describes it.
- **What asks about a key needs a key library installed,** and panics, saying so, without
  one: `KeyPress::from_parts`, `normalize`, a label, `Binding::parse` and `accelerator`,
  and `Keymap`'s reading of saved entries. The key constants, `Binding`'s constructors,
  `registry()`, a `Command`'s id and defaults, and `Keymap::defaults()` ask nothing.
- **`strata-app` installs the key library in `UiThread::claim`,** so every host and every
  `test_support::hosted…` test has it, with the answer that every binding fires. It was
  `keys::Table` ([#2197](https://github.com/lgse/strata/pull/2197)) and is `keys::Xkb` since [#2259](https://github.com/lgse/strata/pull/2259): the table for the keys the code declares,
  and libxkbcommon for the rest, corrected to GDK's answers
  (`docs/rune/shared-state.md`, "What `Xkb` answers").
- **What changed for the press builder when `Xkb` took the table's place: the key a press
  records, and nothing else.** B2 built 3,108 presses through `commands/press.rs` under
  each backend (72 characters of nine scripts, six sets of modifiers, seven origins, the
  QA target's among them). Which catalog commands a press matches in either map, before
  and after the aliases, its `text()`, `letter()`, digit, Latin fallback and modifiers were
  the same in every one. **One character outside those 72 does change its `text()`:** `■`
  (U+25A0). GDK's key for it is `0xadf`, and that key types `▮` (U+25AE), so a press built
  from `■` reports `▮` on `Xkb`, where the table reported `■`. It is the only character
  from U+0020 up that does not come back from `Key::from_char` and `to_unicode`, in GDK and
  in `Xkb` alike. Nothing merged reads a press's `text()`; whoever registers
  type-to-search takes the character Rune delivered, not `text()`, for that one, or
  decides it does not matter. `binding()` differed in the 718 that type a character beyond
  ASCII: the key is now the one GDK has for the character (a legacy keysym for a Cyrillic,
  Greek or Latin-2 letter, where the table gave the Unicode keysym), and a capital beyond
  ASCII is lowered with its Shift kept, as an ASCII one always was. Nothing merged reads
  `binding()` on this interface yet; capture will ([A6](A6.md), [A18](A18.md)), and gets
  GDK's key.
- **Of the eight key cases in [`owner.md`](../owner.md#b3-commands-and-key-dispatch),**
  cases 1 to 6 and 8 read as they did, and case 7, character to keysym, is now GDK's key
  for the character. Rune packet entries 99 and 100 stand as written.
- **Now possible:** a character from any named key (`Key::to_unicode`), the case of any
  letter, the name of any key GDK names, and `normalize` on a non-Latin layout, which finds
  its Latin fallback from a legacy keysym as GDK's does.
- **Still waiting, for the accelerator reader and writer:** a saved keymap.
  `Keymap::overridden` reports a saved entry that names a key as one it cannot read, so the
  shipped keys apply for it, while an entry that unbinds a command still applies; and
  `Binding::accelerator` panics. So every key resolves through `Keymap::defaults()` until
  the reader lands.
- **A keypad key is given as `Typed::Key`,** as GDK reports it, and types its character.
  What any other key typed is given as `Typed::Character`, which goes through
  `Key::from_char`; a named key or a modifier is `Typed::Key`.
- **A plain `#[test]` in `strata-app` that asks about a key calls
  `startup::install_key_library()` first.** The install is one for the process, so a test
  that forgets passes or fails by the order the tests ran in. A hosted test is immune.
- **`keys::set_active` is one slot for the thread, holding a weak reference.** Whoever
  registers keeps the source alive; when it is dropped the catalog reads the shipped
  defaults again. `Fixed` holds the three answers as values, so a change of settings

- **`from_parts` decides whether the press is a modifier from the shared list of
  modifier keys alone.** GTK's reader also takes GDK's word for it; an interface that
  knows more gives the modifier key as `Typed::Key`.
- **A constant for a named key Rune delivers goes in
