## Design

### The oracle: how GTK routes a press

One reader, then three controllers on the window, in this order.

1. **The reader** (`keys::on_press`, `src/ui/keys/mod.rs:102`). A field that is composing
   gets the key first (lines 113 to 124); an armed capture in the window takes every press
   but a lone modifier (126 to 128, `capture.rs:79`); then the press is read through the
   aliases, with `typing` true when a text field or a popover has focus or type-to-search is
   on (129 to 132, `alias.rs:18`).
2. **The tab strip**, a capture-phase controller (`TabWindow::handle_key`,
   `src/ui/window/composition/tabs.rs:754`): Escape cancels a tab drag, then the tab keys
   (`is_tab_shortcut`, line 813). A tab's own dispatcher leaves those keys to it
   (`src/ui/window/keyboard.rs:141`).
3. **The dispatcher**, capture phase, so before the focused widget
   (`src/ui/window/keyboard.rs:132`). `handle_key` (line 421) is a chain: each stage answers
   "not mine" (the next stage is asked), "taken" or "the focused widget's" (the chain ends
   and GTK delivers the key). In its order, with the files under
   `src/ui/window/keyboard/`:

   | Stage | Where | What it reads |
   | --- | --- | --- |
   | `rename_tab` | `focus.rs:35` | Tab in an inline rename |
   | `zoom_shortcut` | `keyboard.rs:466` | Text size, a document's zoom reset, thumbnail size. Before every owner below, so in a dialog too |
   | `input_owner` | `input_owner.rs:19` | Who owns input: a modal layer (line 30) and a native menu (116) get every key; then a column drag's Escape, the footer prompt, the preview's find keys and the F1 reference |

   | `default_tab_navigation` | `focus.rs:43` | Tab in the default map |

   A key the chain leaves goes to `after_yield` (`keyboard.rs:531`): the window actions
   search, jump to folder, terminal, refresh and arrow scope (line 56). An enabled action
   takes its key even when its guard declines to run it, which it does under a modal layer
   or an inline edit (`composition.rs:239`); then a text field's editing keys read through
   the layout fallback.
4. **What the focused widget does not take** bubbles to the Settings key
   (`composition/settings.rs:71`) and last to the native aliases (`alias.rs:45`).

**Chords** are the 10xer stage's state: an armed chord reads the next press first, and most
owners cancel it. The default map has none. **`never_fires`** (`conflicts.rs:312`) is the
part of the conflict check a label uses: a binding no press can reach where its command
acts (no path in that map, a Shift a symbol consumes, a typed key behind the 10xer listing)
or a plain key a user added while type-to-search types it.

**A keyboard-opened menu** targets the browser's focused item when it is selected, else the
folder (`view_filter.rs:78`), anchored at the row's right edge or the pane's middle
(`columns.rs:191`, `browser_modes/context_menu.rs:53`). **What a menu acts on** is the
selection when the entry is in it, else the entry alone (`context_entries`,
`src/ui/browser/context_menu.rs:72`).

### What Rune gives, and what follows

Rune has no capture phase. A key goes to the focused element's `on_key`, innermost first,
then to a focused field's editor, and only then to the window's `on_key`
(`crates/rune/README.md`, "Key routing"). Measured at the pin with a scratch test on the
offscreen host:

- The Menu key and Shift+F10 reach the window's `on_key` after the Columns strip passes them
  on, with `tx.focused()` naming the strip.
- **With a context menu open, the window's keys act today**: Ctrl+H toggles hidden files
  under the menu. GTK gives every key to the menu.

So the routing is in two places, and only two:

- **A view's own keys** are its component's keyboard controller, which sees a key first. It
  is wrapped once, in `strata-app` (see "The Menu key").
- **Everything else** is one function behind the window's `on_key`, which walks GTK's chain.
  What GTK's dispatcher takes before the focused widget and Rune's widget would take first
  is, for the views and the editor mounted today, nothing that differs: the 36 required runs
  show it. A part that finds such a key takes it in its own element's handler and calls the
  same function.

### The registry

A new module, `crates/strata-app/src/commands.rs`, owned by the contract.

```rust
/// The name every route knows a command by: a menu row's id, a header button's, a palette's.
pub(crate) struct Id(pub(crate) &'static str);

/// Where a command acts.
pub(crate) enum On {
    /// Where the keyboard is: a key, a header button, a palette.
    Focus,
    /// The row a menu was opened on.
    Row(At),
    /// A column's folder: a background menu.
    Column(usize),
}

/// One call of a command: where, and the press when a key made it (its digit, what it typed).
pub(crate) struct Call<'a> { pub(crate) on: On, pub(crate) press: Option<&'a KeyPress> }

/// GTK's three answers of a stage.
pub(crate) enum Outcome { Ran, Declined, Left }

pub(crate) struct Action<S: 'static> {
    pub(crate) id: Id,
    pub(crate) keys: Option<Keys<S>>,
    pub(crate) run: fn(&mut S, &Call<'_>, &mut Tx) -> Outcome,
}

/// The keys that run a command, as the GTK stage that owns it reads them.
pub(crate) struct Keys<S: 'static> {
    pub(crate) stage: Stage,
    /// GTK's expression, verbatim: `|press| press.is(RENAME.in_map(Map::Default))`.
    pub(crate) reads: fn(&KeyPress) -> bool,
    /// GTK's guard: `|_, at| !at.text()`.
    pub(crate) when: fn(&S, &Situation<'_>) -> bool,
}
```

- **`Stage`** is `handle_key`'s chain as an ordered enum, one variant for each row of the
  table above under GTK's name, with `TabStrip` first and `AfterYield` and `Unclaimed` (the
  Settings key) last. Two commands on one press are decided by stage, then by the order the
  parts are registered, then by the order of a part's table. That is how GTK decides, and
  what `conflicts.rs` models; with `Keymap::defaults()` it never arises in the default map.
- **Keys resolve through the shared catalog.** `reads` matches catalog constants with
  `press.is(…)` and `press.digit_in(…)`, with `in_map` and `ignoring` as the GTK stage has
  them, so the default-map stages read the default table in both modes and a 10xer action
  reads the 10xer table. `Map::active()` is true on Rune from this package on: the window
  registers an `Active` (`keys::set_active`) that reads the saved `tenxer_mode` and
  `type_to_search` at each press and each view, over `Keymap::defaults()`. A saved keymap
  joins there when B2's reader lands; nothing else changes.
- **An action without keys** is one only a menu row, a button or a palette runs.
- **Builders are `const`**, as `menus::Row`'s are: `Action::new(ID, run).on(Stage::FileCommands,
  |press| …).when(|_, at| …)`.

Three entry points, and nothing else calls a command:

```rust
/// The window's `on_key`: reads the press, finds who has the keyboard, walks the stages.
pub(crate) fn on_key(app: &mut App, event: &KeyEvent, tx: &mut Tx) -> bool;
/// A menu row, a header button, a palette: the command `id`, on `on`. `Declined` when no
/// active part has it, which is how a row or a button is inert.
pub(crate) fn run(app: &mut App, id: &str, on: On, tx: &mut Tx) -> Outcome;
/// The pure half of `on_key`, for a part that hears a key before the window does.
pub(crate) fn route(app: &mut App, press: &KeyPress, at: &Situation<'_>, tx: &mut Tx) -> Outcome;
```

Each wraps the action in `shell::publish` and `shell::settle`, as `shell::on_key` and
`menus::chosen` do today.

### The part hooks

Two, in `slots::Part`, mirrored in `slots::registry::Entry` and `Entry::of`, read over
`Registry::active()`:

```rust
/// What this part's commands do, by any route.
const COMMANDS: &'static [commands::Action<App>] = &[];
/// What this part has of the keyboard now. Replaces `holds_keyboard`.
fn keyboard(_app: &App) -> Option<commands::Holds> { None }
```

`Holds` says which of GTK's owners the part is, and the router holds GTK's rule for each in
one place:

| `Holds` | GTK's owner | Stages that still run |
| --- | --- | --- |
| `Layer` | A modal layer or a menu (`input_owner.rs:30`, `:116`) | `TabStrip`, `RenameTab`, `ZoomShortcut`; `Unclaimed` |
| `Edit` | An inline edit (`commands.rs:85`) | Through `InlineEditing`; `Unclaimed` |
| `Location` | The location bar (`commands.rs:177`) | Through `TextInput`; `AfterYield`, `Unclaimed` |
| `Field` | Any other text field | All: each action's `when` asks `at.text()`, as GTK's stages ask `text_has_focus()` |

The most restrictive answer among the active parts wins. `Situation` carries it, with
`tx.focused()` for a guard that asks where the keyboard is (`at.in_view(app)`). The rename
editor answers `Edit` and the context menu `Layer`, which ends the difference measured
above. `rewrite` gets `typing` from the same answer or type-to-search.

The window's own commands (hidden files, refresh, history, parent, home, and the menu rows
Open and Select All) are a table in `commands/browser.rs`, read after the parts'. Rename's
moves to `rename.rs`.

### The header, and `menus::chosen`

- `shell::bar` builds its five buttons from a table of key, icon, label and command id
  (`toggle-sidebar`, `tab-new`, `search`, `appearance`, `settings`), and each press is
  `commands::run(app, id, On::Focus, tx)`. A package wires its button by registering the
  action; `shell.rs` is not edited.
- A chosen menu row runs the command whose id is the row's id (`open`, `rename`,
  `select-all`, `refresh`, `hidden`), on `On::Row` or `On::Column`. `Wired` and the `match`
  go. A package lights a row by registering an action under the row's id; `menus.rs` is not
  edited. A test holds every row GTK wires today to an action.

### The context-menu opener

```rust
/// Opens the menu of a row of the shown view, or of column `depth`'s folder when `entry` is
/// `None`: what a secondary press and the Menu key ask, in any view.
pub(crate) fn open(app: &mut App, depth: usize, entry: Option<EntryId>, anchor: Rect, tx: &mut Tx);
```

In `menus.rs`. It ends an open rename, as a press outside the field does in GTK; publishes;
finds the entry with the shown view's `Rows::position` and `Browser::entry_at`; applies
`context_entries` once; and builds the folder menu from the browser (`location_at`,
`column_entry_counts`). `Rows` does not grow. "Type to search", which hides a typed hint,
is read by the menu part from `Setup::settings`. `entry_menu`, `folder_menu` and
`context_menu` leave `columns/intents.rs`, with the accessors only they used.

### The Menu key

`commands::view_keys(inner, edge)` wraps a view's keyboard controller in C21's `MenuKeys`,
the one place a view's keys are wrapped: Columns calls it for each column it adds, and
`Pane::new` calls it on the collection it is handed, so Icons has it when its part merges
and List by construction. The key arrives as the `Intent::ContextMenu` a press sends, and
the view's handler calls the opener. `MenuKeys` reads Rune's two chords and not the catalog;
that is right while only `Keymap::defaults()` is read, and `view_keys` is where a rebound
`context_menu` is matched when saved keymaps arrive.

### The press

`commands/press.rs` builds the `KeyPress` from Rune's `KeyEvent`, `tx.physical_key()` and
`tx.key_base()`, and is the only code that does.

- A named key (`Enter`, an arrow, `Function(n)`, `ContextMenu`) is `from_parts` with
  `Typed::Key`. A keypad key with a known position is its keypad key, as GDK reports it.
- `Text(c)` and `Command(c)` are one character with the held modifiers. **Proposed:** read
  it with `KeyPress::from_signal(Key::from_char(c), keycode, held)`, where `keycode` is the
  X keycode of the physical key, or 0 with none. That is the shared crate's own reading of
  the US table, the one `ui::keys` uses for a press without a GDK event, so no third table
  is written. Checked on `keys::Table`: Ctrl+с on the C key is Copy with `used_fallback()`,
  `é` on the 2 key is digit 2, German Shift+7 is `/` with no Shift, Caps Lock is no
  modifier, and with no position Ctrl+Shift+! is still digit 1. The trap B2 names does not
  bite, because the character is given as `Key::from_char`, never as a legacy keysym. B2's
  note asks for `from_parts`; that needs the US table public in the shared crate, which is
  B2's file. **This is the one thing to rule before the second pull request.**
- Composed text of several characters is `Typed::Nothing`: no shortcut, no single character.

The seven cases, and the default each gets, go into `owner.md` with that pull request:

| Case | The builder does | As GTK? |
| --- | --- | --- |
| 1. Another Latin layout configured | The US position | No: Rune cannot see the other layouts |
| 2. The digit row above level 1 | With a base character known, a character that is neither the base nor typed with Shift has no position, so it is a digit only if it types one | Yes in a window; not in the QA target |
| 3. Keypad decimal and separator | The keypad key itself where the position is known, which needs `KP_Decimal` and `KP_Separator` declared (GDK names both); until then `.` and `,` | Asked of the orchestrator |
| 4. The QA target | No position and no base, so the US table reads the character: exact on a US layout, which every required run uses | Packet entry 97; a workaround outside Rune is H3's |
| 5. Keys Rune never delivers | Nothing arrives | Nothing to route |
| 6. A modifier's own press | The shell does not ask Rune for them; if one arrives, `held` is built without it, as GDK reports | Yes |
| 7. Character to keysym | `Key::from_char`, B2's one keysym for a character | B2's |

From [B2](B2.md), with the catalog's move ([#2195](https://github.com/lgse/strata/pull/2195)):

- **What is there:** `strata_desktop::keys` has `Key`, `Modifiers`, the catalog
  (`keys::bindings`), `registry()`, `Keymap`, `KeyPress` with `from_parts`, `rewrite` and
  the labels. `docs/rune/shared-state.md`, "The key catalog", describes it.
- **What asks about a key needs a key library installed,** and panics, saying so, without
  one: `KeyPress::from_parts`, `normalize`, a label, `Binding::parse` and `accelerator`,
  and `Keymap`'s reading of saved entries. The key constants, `Binding`'s constructors,
  `registry()`, a `Command`'s id and defaults, and `Keymap::defaults()` ask nothing.
- **`strata-app` installs `keys::Table` in `UiThread::claim`** ([#2197](https://github.com/lgse/strata/pull/2197)), so every host and every
  `test_support::hosted…` test has it, with the answer that every binding fires. B3
  installs nothing and can start. What the table answers is in
  `docs/rune/shared-state.md`, "What `Table` answers".
- **With the table, B3 can:** build presses with `from_parts`; match every catalog entry in
  both maps; run `rewrite`, `letter`, `text` and `digit_in`; label every entry and build
  the reference's search text in all thirteen languages; and resolve through
  `Keymap::defaults()`.
- **Until B2's `xkbcommon` backend or its accelerator reader, B3 cannot:** read or write a
  saved accelerator string; get a character from a named key beyond the keypad; rely on
  `normalize` or `KeyPress::from_signal` on a non-Latin layout; change the case of any
  letter but an ASCII one; or name a key the code does not declare.
- **`normalize` and `from_signal` are a trap on the table.** They read a non-Latin key's
  character to decide the Latin fallback, and the table has no character for a legacy
  keysym such as `Cyrillic_es`. A press built that way on a Russian layout gets no
  fallback, so Ctrl+С is not Copy. B3 builds such a press with `from_parts` and works out
  the fallback itself, or waits for the `xkbcommon` backend.
- **A keypad key is given as `Typed::Key`,** as GDK reports it: the table answers the
  character of the sixteen keypad keys that type one, so `text()` of a keypad digit is the
  digit, as on GTK. What any other key typed is given as `Typed::Character`, which goes
  through `Key::from_char`; a named key or a modifier is `Typed::Key` and types nothing.
- **Only ASCII letters have another case on the table,** so `from_parts` lowers `C` and no
  other letter: give a non-ASCII letter already lowered.
- **Saved keymaps wait for the accelerator reader.** `Keymap::overridden` on the table is
  partial: a saved entry that names a key cannot be read, so the shipped keys apply for it,
  while an entry that unbinds a command still applies. And `Binding::accelerator` panics.
  So B3 resolves through `Keymap::defaults()` until the reader lands.
- **A plain `#[test]` in `strata-app` that asks about a key calls
  `startup::install_key_library()` first.** The install is one for the process, so a test
  that forgets passes or fails by the order the tests ran in. A hosted test is immune.
- **`keys::set_active` is one slot for the thread, holding a weak reference.** Whoever
  registers keeps the source alive; when it is dropped the catalog reads the shipped
  defaults again. `Fixed` holds the three answers as values, so a change of settings
  means registering a new one, or B3 implements `Active` on something it already keeps.
- **`from_parts` decides whether the press is a modifier from the shared list of
  modifier keys alone.** GTK's reader also takes GDK's word for it; an interface that
  knows more gives the modifier key as `Typed::Key`.
- **A constant for a named key Rune delivers goes in
  `crates/strata-desktop/src/keys/key_constants.rs`,** whether or not the catalog binds
  the key: X's keysym name, the value from `xkbcommon-keysyms.h`. While GTK exists each
  must be a name GDK reads, which a GTK-lane test checks; a key GDK does not name is
  raised in this file and in [`owner.md`](../owner.md) before it is added.
- **Which bindings never fire** is an answer the interface installs with its backend
  (`NeverFires`); a label leaves such a binding out. GTK answers from its conflict check.
  What the Rune side answers is open ([`owner.md`](../owner.md#b2-shared-state-out-of-the-gtk-package)).
