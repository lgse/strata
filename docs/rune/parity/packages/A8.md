## Notes from other packages

From [B1](B1.md) (2026-11-12): **the shown view is chosen once, at start.**
`slots::Registry::new` picks the view whose `shows` answers to the saved `browser_mode`, or
the first registered one; nothing changes it afterwards. A view that is not shown has no
listener and has missed every `Browser` event since start. So a live switch needs two things
in the contract, a setter for the shown view and, for the view that becomes shown, a listener
and a rebuild from the browser: a `contract` change of this package's. Parts are held to "a
part can build everything it shows again from the browser", so the rebuild has something to
stand on. The header's Appearance button is wired through [B3](B3.md)'s commands.

From [B2](B2.md) (2026-11-12): **for a folder's saved view, wait for the folder-view
store.** The model and the file code have moved ([#2168](https://github.com/lgse/strata/pull/2168), [#2188](https://github.com/lgse/strata/pull/2188)); the store, with
`begin_write`, `finish_write` and `adopt`, is B2's last pull request. Until it lands a part
does not call `load_folder_views` or `save_folder_views` itself: on GTK a saved view is read
behind `remembered_key` and the key rules of `key_for_location`, the file is read once in a
process, and two writers in one process would each save without the other's changes.

- **When a write is scheduled stays in each interface:** a change wants a write in 500 ms,
  opening a folder one in 60 s, and a pending timer is kept unless the new delay is shorter
  (delays compared, not deadlines). The two delays are exported as constants. This package
  writes the Rune side's scheduling from its loop; nothing tests the 60 s delay, the
  keep-unless-shorter rule or a touch-only write today.
- **Nothing on Rune starts the folder-view write at exit.** GTK calls
  `flush_pending_folder_views` before it quits; `crates/strata-app/src/host/windowed.rs`
  flushes the settings writer only.
- `key_for_location` reads `strata-fs`'s thread-local mount snapshot: the interface thread
  only.
- The policy that spans the settings and the folder views stays in `src/ui`'s wrapper; where
  it lives for Rune is open ([`owner.md`](../owner.md#b2-shared-state-out-of-the-gtk-package)).
- A sort chosen in a folder is stored for that folder on GTK while per-folder settings are
  on; the Rune side always stores it as the default. This package and [A10](A10.md) meet it.

From [B2](B2.md) (2026-11-12), **the folder-view store has landed** ([#2262](https://github.com/lgse/strata/pull/2262)):
`strata_desktop::settings::FolderViewStore`, described in `docs/rune/shared-state.md`, "The
store". What a part of this interface does with it:

- **One store for the process,** loaded once at start-up (`FolderViewStore::load()`), held
  where the window holds state. A second store would save without the first's changes.
- **Reading and changing:** `views()` and `views_mut()`, with a key from `key_for_location`
  (the interface thread only). The store does not carry the gate: on GTK a saved view is read
  and written only while `remember_folder_views` is on, a value equal to the default is not
  stored, and a change of a default prunes what now equals it. Those bodies are in
  `src/ui/preferences/folder_view_settings.rs`; the one that is needed moves, or is written
  again, in the package that needs it, as "The rule for a setter's body" says.
- **Writing:** the interface owns the clock. After a change ask for a write in
  `FOLDER_VIEWS_SAVE_DELAY`, after a folder was only opened in `FOLDER_VIEWS_USE_SAVE_DELAY`,
  on one timer that keeps its time unless a shorter wait is asked for. Then `begin_write`,
  await `finished()` where the interface awaits things, and act on `Written`: `Busy` asks
  again; `Saved` adopts what came back, shows it, and then calls `finish_write`.
- **At exit** a store with unsaved changes writes once more with `exit` set. Nothing on
  this interface does that yet.
- **When the file changes under the process:** `FolderViewStore::reread()`, then `adopt`.
  Nothing on this interface watches the file yet.
- **Where `finished()` is awaited:** in practice in a task spawned on GLib's context, as
  `settings::Saved::change` awaits the settings' save. GLib dispatches the end of the write
  while Rune holds the application state, so the task only queues the `Written`; `adopt` and
  `finish_write` run when the queue is applied, in `poll` or in an update.
- **Two things the types do not prevent,** and what each costs:
  - *Dropping `merged` and going straight to `finish_write`.* The file is right: every write
    merges over what is there. This process's values stay without the other process's until
    its next write, which comes back with them again, or until a reread has something to
    adopt, and a reread has nothing while this process wrote the file last.
  - *A second `begin_write` while one is out.* Both reach the file in order, each merged over
    it, and the second carries the first's changes again. `finish_write` in either order
    counts the same changes as saved.
- **A `merged` adopted late can put older values back.** `adopt` lets what it is given win
  for every folder with no unsaved change here. Adopted after a newer reread, or after a
  later write's, it brings back what the other process had saved earlier, until the next
  write or reread brings the file's. GTK adopts the same way, in the task that awaited the
  write. Here a result also waits in the queue, so apply results in the order they arrived.
