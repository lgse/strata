## What dependents must know

- **Undo and redo are commands `undo` and `redo`** (`crates/strata-app/src/undo.rs`), read at
  GTK's `text_input` stage outside a text field: Ctrl+Z, and Ctrl+Shift+Z or Ctrl+Y. A menu
  row or a button runs them by those ids. A key with nothing to replay is not taken.
- **A replay with an item in the way stops as the conflict prompt's Cancel does**, and its
  entry stays: GTK asks there (`resolve_replay_collisions` in
  `src/ui/browser/transfer/replay.rs`), and the prompt is [A12](A12.md)'s. The note in
  A12's file says where it plugs in.
- **Not shown:** the card GTK shows while a replay checks the disk, and the Trash undo's
  fly-out to the trash button.
- **New Folder and New File are commands `new-folder` and `new-file`**
  (`crates/strata-app/src/new_item.rs`): Ctrl+Shift+N at GTK's `file_commands` stage, and
  the menus' rows by their ids, in the row's or the folder's column. The editor opens on the
  created item through `rename::begin_new_item` with `Naming::NewItem`, and the typed name
  goes to `Browser::name_new_item` (a path, to `place_entry` with `new_item`), so one undo
  trashes the item under its new name. Escape before the editor opens gives up the naming
  (`new-item-cancel`, at `inline_editing`).
- **A rename the browser fails shows GTK's "Unable to rename item" dialog**
  (`crates/strata-app/src/rename_failed.rs`), the first part in the `Dialogs` slot: C15's
  `StrataDialog` with the browser's message, one Close button that has the keyboard, and
  `Holds::Modal { field: false }` while it is open. The editor no longer opens again with the
  message. A rename Tab moved on from takes the cursor back and closes the neighbour's editor
  first, as GTK's `fail_pending_rename_from_browser` does. GTK shows the same dialog for other
  failures; a package that needs it for another command can make it the window's.
- **Deleting is the commands `trash` and `delete`** (`crates/strata-app/src/trash.rs`):
  Delete and Shift+Delete in the default map at GTK's `dismissal` stage, outside a text
  field, and the entry menu's Move to Trash and Permanently Delete rows. A permanent delete,
  Delete in the Trash, and a trash where the location deletes but cannot trash ask first in
  GTK's confirmation (`trash/dialog.rs`, in the `Dialogs` slot, `Holds::Modal` while open).
  A trash that some items fail for want of Trash support asks to delete those for good.
  "Completed with errors", for every other partial failure, waits for the window's error
  dialog (A5).
- **A new item does not clear the column's filter first**, as GTK's `begin_new_entry` does:
  the filter is [A10](A10.md)'s, and the note in its file says where it goes.

## Open

- "Completed with errors" (`show_partial_failure_dialog`, and `show_delete_error_dialog` with
  its retry button) is not shown: a partial failure with nothing to retry, or with other
  failures beside the retryable ones, is only logged. It waits for the window's error dialog,
  which A5 makes from `rename_failed.rs`.
- The delete confirmation shows a file link's size with the total, where GTK shows each as
  it is found, and leaves out the dissolve of the deleted rows and 10xer's confirm key
  (A11).
- Columns' background click selects the column's first visible entry by `visible_range()`
  (`background_click` in `crates/strata-components/src/columns/view.rs`), the range Rune
  reported a frame ago: after an entry is listed above in the same frame it could select the
  one before. Noted from #2283's review, not checked against GTK, not changed.
- New Folder with Selection (Ctrl+Alt+N) is not bound: the folder takes the selection in by
  a move, a transfer, and its run `new-folder-with-selection-groups/columns` waits on
  finding [#2162](https://github.com/lgse/strata/issues/2162) and an owner ruling. Unbound,
  it also loses GTK's fallback to a plain New Folder when nothing is selected
  (`file_commands` in `src/ui/window/keyboard/commands.rs`).
- A pointer press or a scroll anywhere in the window gives up a naming that waits on GTK
  (`install_inline_edit_dismissal` in `src/ui/browser/inline_edit.rs`). Parts have no
  pointer hook, so on Rune a click elsewhere during the wait is overridden by the next poll,
  which opens the new item's editor. A hook is a `contract` change; recorded, not built.
- F2 on the created item itself while it waits: GTK takes the naming over and opens the
  editor with `Naming::NewItem`; on Rune the naming is given up and a plain rename opens. F2
  or the menu's Rename on any other entry gives the naming up on both.
- The created item is not scrolled into view before its editor opens
  (`scroll_created_into_view`); the editor shows its row when it begins.
- The failed rename's dialog differs from GTK's in two small ways. A second failure while
  one is open replaces its message on Rune, where GTK stacks a second dialog over the first.
  And GTK's message body is selectable (`append_detail` in `src/ui/modal/messages.rs`),
  where C15's message text is not.
- Unverified: on GTK, a dialog taking the keyboard from a field Tab had moved to its
  neighbour submits what was typed there; on Rune that field is closed without renaming
  (`failed` in `rename.rs`).
- The undo conflict prompt waits for [A12](A12.md) (see "What dependents must know").
- The card GTK shows while a replay checks the disk is the progress dock's (C16
  `ProgressDock`), and the Trash undo's fly-out is C23's trash flight: whoever mounts each
  shows it for undo too.
- `Undo::checking` is per window, where GTK's `preparing_transfers` is per tab (a
  `ViewState` each). Whoever adds tabs keys the check by browser and hands its answer to the
  browser that started it. The same note is in [A4](A4.md).
