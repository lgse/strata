## Notes from other packages

From [B1](B1.md) (2026-11-12): **what the Rune QA backend still assumes of a view.** The
backend names no view: it reads the shown one through `shell::shown_view(app)` and its
`Probe` (`name`, the pane's mark; `roles`, Rune's roles of an entry list and an entry;
`lists`, the keys of the entry lists; `listed`, for `ready`). What `qa/tree.rs` and
`qa/stage.rs` still take for granted, and a second view may not satisfy: a pane is the
nearest named `group` above an entry list; a row behind an open menu is found by the
collection's `row-…` key and its name by the collection's `LABEL` key; and `qa/roles.rs`
maps only the Rune roles it lists to the scenarios' AT-SPI names, so a grid or a table needs
entries there.

**Ownership**, a default of the orchestrating session for the owner to confirm: `qa/` is
this package's. An area adds its own steps and predicates in files of its own; a view whose
panes do not fit does not edit `qa/` in passing, but opens a `contract` pull request agreed
with this package ([`owner.md`](../owner.md#b1-shell-seams)).

From [A5](A5.md) (2026-11-13, by the coordinator's ruling): **the backend presents buttons
behind an open menu.** `qa/stage.rs`'s `drawn_buttons` reads every keyed, named button drawn,
and `qa/tree.rs`'s `add_hidden_button` adds under the window each one the tree left out while a
menu is open (a node of role `menu` that is modal; a dialog's modal does not count), by key,
label and box only, as `add_hidden_column` does for Columns rows. It skips a button that is
drawn at no opacity or has none of it in view (a crumb scrolled out of its strip). It does not
skip an inert one: behind a modal Rune makes everything else inert, the buttons this is for
included (A5's [#2307](https://github.com/lgse/strata/pull/2307) found it, and dropped the check #2303 had). So a button made
inert by its own `.inert()` would be presented too; Strata's inert subtrees are decoration.
`keyboard_navigation/back-history-dropdown` lets go of a press held on Back at line 15 with
Back's history open. What a presented button does not carry:
- **its state:** it reads `sensitive` whatever it is (`!has_state("disabled")` in `backend.rs`,
  and Rune's drawn elements say nothing of being disabled), and it is not focusable and offers
  no click action, so a run asserting a state of a button behind a menu needs an `a11y` twin;
- **its place:** it hangs off the window's root, so a target `within` a pane misses it and
  `nth: -1` picks it first;
- **whether it is hidden from assistive technology on purpose:** Rune's `ElementInfo` has no
  `a11y_hidden` flag, so a keyed button hidden that way could still be presented behind a menu.

Tests: `qa::tree::tests::a_button_behind_an_open_menu_is_presented_from_what_is_drawn` and
`qa::stage::tests::only_a_button_in_view_and_drawn_is_presented`.

## What dependents must know

- **The List view is a `list` of `list item`s with heading `button`s on Rune**, as on GTK
  (#2324); Rune's roles are `list` and `listitem` (`Roles::LIST`). A scenario aims at a List
  row as `list item` and at a heading as `button`.

- **An entry's icon is an `image` under its row on Rune**, the drawn `ICON` element's box. A
  drag aimed at an entry starts on it, as on GTK.

- **An entry's row has a `panel` on Rune**, with the row's own box, as GTK's row has the box
  its content is drawn in.

- **A Rune run's screenshots are text:** `<name>.txt`, the tree as of the step, beside where
  the `.png` would be, and `screenshot.txt` at the end. No Rune run can assert on pixels.

- **A run starts in its mode's view or not at all.** On Rune, `ready` fails a run whose saved
  `browser_mode` no mounted view answers to (`View::shows`), naming the mode and the view the
  shell fell back to. A package mounting a new view registers its `shows` before its runs can
  start.
- **A remembered row is gone once its column's entries are replaced** (`EntriesReplaced`, as
  after F5), on Rune as on GTK: `replaced` holds and `remembered` finds nothing. Rows the
  browser inserts, splices or fills keep it. Only `EntriesReplaced` is modelled: GTK also
  makes a new row widget on a view rebuild (`rebuild_icons`, `rebuild_list`), on a filter
  hiding and showing the row again, and on the row scrolled out and back, where Rune keeps
  the row. A run that relies on one of those needs `qa/replaced.rs` extended first.

- **One Rune mutation patch is proven alone with `./scripts/qa-parity.sh mutations <scenario>`**
  (or `<scenario>-rune` for a twin's), with the files it touches clean. Nothing is applied by
  hand any more.

- **A pane's viewport is the scroll pane inside its entry list, when it holds one.** A view
  whose list holds its scroll viewport (every C1e collection) needs nothing more; one whose
  list sits in a scroll pane is read as on GTK. A scroll pane inside an entry is never the
  pane's.
