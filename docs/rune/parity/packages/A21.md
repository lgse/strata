## What dependents must know

- **One settings store for the process.** `shell::saved(app)` is the window's way into it.
  A part that keeps its own copy of a setting, beyond what it reads at use, follows another
  window's change only if `shell::follow_another_window` makes it: add the call there.
  `Saved::share` gives a new window the store, the floating chooser's included;
  `startup::load_settings` makes a new store, so two windows that each call it lose each
  other's saves (the portal process's choosers have one each).
- **A window's start.** A window opened with no argument restores the saved session and
  persists its tabs, as every window GTK's `present` opens does: `launch::Initial::Plain`, the
  process's own launch, reading `tabs.toml` at start-up, and `Initial::Present`, a later one,
  reading it off the interface thread. Several such windows each save their own tabs, and the
  last to change them wins, as on GTK. A window on an argument (`Initial::Argument`) or a test's
  folder (`Initial::Explicit`) leaves `tabs.toml` alone. This supersedes [A4](A4.md)'s note
  below, which asked for a later launch to persist nothing.
- **Waking a window.** Whatever queues into another window's queue from outside its own
  handlers wakes it: the windowed host wakes every window with an update queued after each
  dispatch and each committed setting (`host::windowed::wake_pending`). A new process-wide
  service that queues into a window from elsewhere calls it too.
- **The QA mode with several windows.** Steps act on the run's window, root `window`; keys and
  the pointer go to it, or to A20's floating chooser in front of it. A launch's windows stand
  behind it in the merged tree, so `within: {"other_window": "Strata"}` works for reads and
  `activate`. A launch's window takes the window focus from those before it
  (`Runtime::window_focus`), as on the runner's Xvfb: the run's window then reports that it
  lost the keyboard, though the keys still go to it.
- **The window's presence** is every tab's browser's (`shell::presence`): `Focused` with the
  keyboard, `Visible` without, `Hidden` off screen. A part that should follow it, as GTK's path
  completion follows `BrowserView::set_presence`, hears the window's focus through the root's
  `on_window_focus` (`location::window_focused` does).
- **FileManager1** is served by the primary: a `dbus_send` to `org.freedesktop.FileManager1` in a
  run with `session_bus` opens a window per folder (`Opening::Reveal`).

## Open

- **GTK's argument card.** GTK mounts an argument that needs mounting, shows "Connecting to
  location…" with Cancel after a second, and "The requested location is unavailable" with
  Retry in the pane when GIO has no answer (`src/ui/window/open_argument.rs`). The Rune side
  opens such an argument as a location and lets the browser report it. No run covers it.
- **The session host serves no launch**: its QA mode does not claim the bus, and its backend
  reads one window. No session-host run launches, so it is deferred (the plan, item 2).
- **Each window keeps its own per-folder-view store and thumbnail store.** Two windows
  converge on the folder views through the file, as two processes do. Slice 2b makes one of
  each for the process.
- **A Wayland window that is minimized stays `Visible`.** Rune reports neither covering nor
  minimizing on Wayland, where GTK reads `MINIMIZED` from the toplevel's state
  (`crates/strata-app/src/shell/presence.rs`). A browser then rechecks its folders as for a
  window in view.
- **The activation token is not tested in a real window.** sway gives a new window the focus
  without one, so the window tests cannot tell it was used; `application::tests` covers that
  each window is created with the token its asker forwarded.
- **The pump goes through one window.** A view change in another window reaches its browser at
  that window's next `poll`, not before a dispatch the active window runs
  (`crates/strata-app/src/host/windowed.rs`, "Windows"). What the dispatch queues for the
  other window wakes it at once (the review fixes below), so its next `poll` does come.

From [A4](A4.md) (2026-11-14, [#2474](https://github.com/lgse/strata/pull/2474)): **GTK's close guard holds on the window's own Close buttons
and on closing its last tab, not yet on a close the window manager asks for.** GTK refuses
every close request while a tab's browser has a file operation running, and says "File

the window goes and cannot keep it (at `2a44156`): that half is finding
[#2473](https://github.com/lgse/strata/issues/2473) (`rune-gap`), for this package to draft
into the packet with the rest of the window's lifecycle, and to work around if it can.
GTK's application-wide guard for running jobs ("Background jobs are still active",
`src/ui/jobs.rs`) has no Rune side yet either.
